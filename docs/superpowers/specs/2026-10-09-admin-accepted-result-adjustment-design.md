# 管理员调整正式录取结果设计

## 目标

赋予现有管理员在当前进行中周期内修正正式录取结果的能力，用于处理已经结算或公布后发现的录取去向错误。管理员可将学生改录到该生本周期已提交的另一项志愿，或取消该生当前录取。每次调整必须填写原因，保留可审计的前后记录，并保持学生、课题、教师和调剂记录一致。

## 已确认的现状

- 管理员 API 已覆盖 `/api/admin` 与 `/api/selection-admin`，但现有功能没有直接调整正式录取的操作。
- 首轮结算通过 `applications.status = 'accepted'` 写入结果，并同步更新课题 `published/full` 状态。
- 调剂自动匹配也写入 `applications`；调剂志愿结果保存在 `adjustment_volunteers`。自动匹配汇总保存在 `adjustment_settlements.result_json`。
- 学生结果页从当前周期的 `applications` 中读取 `accepted` 记录。
- 操作日志表已支持记录管理员、动作、对象、JSON 详情及 IP，无需新增表结构。
- 自动匹配结算与统一结算均可能在周期结果公布后完成；其算法汇总代表原始结算结果，应保留为历史快照。

## 方案比较

1. **原子地调整现有正式结果（推荐）**：在单一事务内更新对应的首轮申请和调剂志愿记录、课题状态、通知及操作日志。学生结果继续以 `applications` 为唯一当前结果来源，改动集中且可直接审计。
2. **重新运行整周期结算并注入管理员决定**：可沿用自动匹配器，但会重算其他学生，可能改变无关录取结果和通知，不适合作为单个学生的人工修正。
3. **新增结果覆盖表**：保留基础结果并在所有结果页、统计、容量校验和导出中叠加覆盖记录。该方式需要改造更多读路径，并形成双重结果来源。

采用方案 1。管理员调整是结算完成后的定点修正，不重跑全周期匹配器，也不覆盖结算汇总快照。

## 范围与业务规则

- 周期范围：`getActiveCycle()` 返回的进行中周期（状态为 `active`、`selection`、`review` 或 `adjustment`）；归档或已结束周期不提供调整入口。
- 可调整对象：当前周期已有正式录取的学生。目标课题必须已有该生本周期的申请/志愿记录。允许该记录因结算曾被标为 `withdrawn` 或 `rejected`，管理员改录时将其恢复为 `accepted`。
- 取消录取：将当前 accepted 记录改为 `withdrawn`；相关调剂志愿同步为 `withdrawn`。学生此后不再有本周期正式录取。
- 更换课题：原 accepted 记录转为 `withdrawn`，目标申请转为 `accepted`，同一学生不得同时保留多条 accepted。相关调剂志愿状态同步为 `accepted/withdrawn`。
- 课题必须属于当前周期且可招生。正式录取名额与教师本周期正式录取总上限均为硬性限制；核算目标容量时排除该学生当前的旧录取。违反任一上限则整笔拒绝，不提供超额绕过开关。
- 该操作不允许创建学生从未填报的新课题志愿，不修改志愿顺序、教师评审草稿或其他学生的结果。
- 每次调整要求填写非空原因。操作日志记录周期、学生、原录取申请/课题、目标申请/课题、调整类型、原因、操作管理员和客户端 IP。
- 学生收到其结果已更新的站内通知；原导师与新导师（如有变更）收到录取调整通知。通知与数据变更在同一事务中写入，避免数据成功而通知缺失。
- 自动结算汇总保留原样，作为当时算法结果快照；当前结果页和容量统计仍以应用记录状态为准。

## 管理员交互

在管理员“学生选课情况”或可检索的申请管理页加入“调整录取”入口。管理员可按学号/姓名找到当前已录取学生，查看其当前课题及本周期全部既有志愿，选择“改录”或“取消录取”，填写原因并查看操作前后的结果预览。提交前用二次确认展示学生、原课题、目标课题或取消动作及原因；成功后刷新当前结果和名额统计，失败时保留表单内容并展示服务端原因。

只有当前周期存在正式录取时显示入口。目标课题显示课题名、导师、志愿序号、当前课题已录人数/上限及导师已录人数/上限；课题或导师无余量时不可选。取消录取不要求目标课题。

## 服务端与数据一致性

- 新增管理员专用调整 API，受现有 admin 角色中间件保护；不能复用教师评审 API。
- 在事务中锁定周期、学生、其当前周期申请记录、涉及的课题和相关调剂志愿，再按锁定后的数据重新核验当前录取唯一性、目标志愿归属和两类名额。
- 如果首轮或调剂结算正在运行，拒绝管理员调整，避免与匹配写入交叉；结算已完成后可在周期仍进行中时调整。
- 更新 applications，并同步同周期对应 adjustment_volunteers；仅把涉及的课题状态按新 accepted 计数重算为 `published/full`，其他人工关闭状态保持不变。
- 事务内追加 `operation_logs`，并写学生及受影响导师通知。任一校验或写入失败，所有记录回滚。
- 不改 `selection_settlements.result_json` 或 `adjustment_settlements.result_json`，避免把人工修正伪装成原始算法结算结果。

## 验收标准

- 管理员能将已录取学生改到其当前周期的另一项已提交志愿，学生结果页显示唯一的新录取。
- 管理员能取消录取，学生结果页不再显示该生已录取。
- 非管理员不能调用调整 API；无正式录取学生、非当前周期申请、未填原因或无效目标均被拒绝。
- 满课题和教师达上限会阻止调整；发生容量冲突时当前录取及相关记录不变。
- 调整后源/目标课题满额状态、调剂志愿状态、操作日志和通知保持一致；结算汇总快照不被重写。
- 事务并发时不会造成同一学生多重录取或超出容量。

## 不在本次范围

- 修改已结束周期的历史结果。
- 允许课题名额或教师上限超额。
- 将学生改录到其本周期未曾填报的课题。
- 重跑自动匹配，或自动重排其他学生。
- 新增独立“超级管理员”角色；当前全局 admin 角色即有此能力。
- 删除历史数据或提供自动撤销；修正错误时管理员再次执行相反的正式调整并填写原因。
