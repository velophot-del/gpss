# GPSS 调剂志愿与统一结算设计

**状态：已通过，待实施**

## 1. 目标与边界

将当前“单课题调剂申请、管理员逐条确认”的流程替换为独立的调剂志愿轮次。

- 仅本周期未录取学生可参加调剂。
- 学生仅可查看和填报与本人 `major_code` 相同的、本周期已发布且仍有名额的课题。
- 学生一次提交 3–6 个不重复、连续编号的调剂志愿，并至少覆盖两位教师。
- 教师对本课题的调剂学生保存拟录取、候补或不录取草稿，提交后等待统一结算。
- 全部有调剂申请的课题提交，或达到调剂截止时间后，系统统一结算；每名学生最多录取一个课题。
- 首次志愿的志愿序号、申请理由与首次结算日志保持可追溯；调剂录取作为后续正式结果写入，并记录“来自调剂志愿”的审计信息。
- 下线学生单课题调剂申请和管理员逐条录取操作；已有 `adjustments` 记录保留为历史数据，只读展示。
- 学生角色在任何阶段浏览选题时隐藏教师姓名、职称、院系、邮箱、电话和头像；教师信息保留在数据库、教师端和管理员端，不删除也不影响教师遴选、通知或后续管理。

调剂结算不使用 GPA 自动排序。教师的拟录取/候补排序、学生调剂志愿顺序、课题剩余名额及教师指导上限共同决定结果。

## 2. 状态与权限

### 2.1 学生

学生可在 `adjustment` 阶段提交或整组覆盖自己的调剂志愿。学生可修改，直到任一已填报课题的教师名单被提交或系统开始结算；此后整组志愿冻结并返回 `409`，避免教师已提交的名单与学生最新志愿不一致。

学生资格：当前周期没有 `accepted` 申请，并且存在首次志愿记录。学生调剂志愿提交后，页面显示“等待教师遴选/统一结算”，不展示教师草稿决定。

### 2.2 教师

教师仅在 `adjustment` 阶段处理本人仍开放且有剩余名额的课题。每位申请人可标记为：

- `proposed`：拟录取，按连续 `decision_rank` 排序；
- `reserve`：候补，按连续 `decision_rank` 排序；
- `reject`：不录取；
- 未处理：不进入要约序列。

保存草稿不改变正式 `applications.status`。提交后批次只读；结算开始前，管理员可退回给教师修改。教师能查看学生的专业、班级、调剂志愿序号、申请理由、个人陈述、技能标签与兴趣方向。

系统提供“匹配提示”协助教师判断：课题 `tags` 与学生技能标签的完全匹配项、课题 `category` 与学生兴趣方向的匹配项，以及由两者构成的提示分数。提示只用于展示和排序辅助，不自动录取、不替代教师排序，也不改变统一结算规则。

### 2.3 管理员

管理员在“调剂结算”页面查看：资格学生数、调剂志愿提交量、每课题教师提交状态、截止时间、配置错误与结算状态。管理员只能在结算未开始时退回已提交课题；结算失败可重试。管理员不再逐条决定学生录取。

### 2.4 学生选题教师信息隐藏

该规则适用于学生角色的课题列表、课题详情、选题工作台、推荐列表、调剂志愿页及学生端选题结果展示，且不随周期阶段变化。

- 数据库中的 `topics.teacher_id`、教师用户资料和既有教师信息字段完整保留。
- 教师和管理员接口保持现有教师信息，不受影响。
- 学生端不渲染教师姓名、职称、院系、邮箱、电话和头像；学生接口响应也不下发这些展示字段，避免通过浏览器网络响应获取。
- 为保持“至少覆盖两位教师”的志愿规则，学生接口只下发不可反查教师身份的 `teacherGroupKey`，前端仅用它计算覆盖数量，不显示该键。
- 学生被正式录取后的教师关联继续由服务端用于任务书、指导记录和通知；该规则只限制学生查看选题及选题结果中的教师身份展示，不删除关联数据。

## 3. 数据模型

新增四张表，避免与首次志愿和首次遴选批次混用。

### 3.1 `adjustment_volunteers`

调剂志愿主数据。

| 字段 | 含义 |
|---|---|
| `id` | UUID 主键 |
| `cycle_id` | 选题周期 |
| `student_id` | 学生 |
| `topic_id` | 调剂课题 |
| `priority` | 1–6 连续志愿序号 |
| `motivation` | 调剂申请理由 |
| `status` | `submitted`、`accepted`、`rejected`、`withdrawn` |
| `created_at`、`updated_at` | 审计时间 |

唯一键为 `(cycle_id, student_id, topic_id)`；为 `(cycle_id, student_id)`、`(topic_id, status)` 建立索引。

### 3.2 `adjustment_batches`

每个周期、每个课题一份教师调剂名单。字段与首次 `selection_batches` 对齐：批次状态 `draft`、`submitted`、`auto_submitted`、`settled`，乐观锁 `version`，提交人、提交时间、自动提交时间、结算时间和审计时间。唯一键为 `(cycle_id, topic_id)`。

### 3.3 `adjustment_draft_items`

教师对调剂志愿的决定。字段为 UUID、`batch_id`、`volunteer_id`、`decision`、`decision_rank`、`comment`、`updated_by` 和审计时间；唯一键为 `(batch_id, volunteer_id)`。

### 3.4 `adjustment_settlements`

每周期一条调剂结算记录，状态为 `pending`、`running`、`completed`、`failed`；记录触发方式（全部提交、截止自动、管理员重试）、结果 JSON、错误信息、开始和完成时间。`cycle_id` 唯一。

## 4. 学生流程

1. 管理员将周期切换到 `adjustment`，并设置有效的 `phases_config.adjustment.end`。
2. 合格学生进入“调剂志愿”页，查看同专业且未满员的全部发布课题。
3. 学生收藏并排序 3–6 个课题，填写每项调剂理由后整组提交。后端验证课题周期、发布状态、专业代码、名额、志愿连续性及至少两位教师。
4. 学生可在涉及课题名单尚未提交时修改并再次整组提交；系统保留同一志愿行并更新内容与顺序。任一涉及课题名单提交后，整组志愿冻结。
5. 结算完成后，学生查看唯一调剂结果；未录取学生显示“本轮调剂未匹配”，由管理员决定是否开启下一轮。

## 5. 教师与统一结算流程

1. 教师进入“调剂遴选”，逐课题查看调剂申请人和完整学生档案。
2. 教师设置拟录取、候补和不录取，调整拟录取/候补排序，保存草稿。
3. 教师提交本课题名单。所有有调剂申请的课题都提交后，立即触发结算；截止时由后台任务自动提交未提交草稿。
4. 结算使用现有确定性匹配核心：课题先按拟录取、候补及教师排序发出要约；学生只保留其编号最小的调剂志愿；释放的名额继续向候补递补。
5. 结算将命中的 `adjustment_volunteers` 标记为 `accepted`，其他同一学生调剂志愿标记为 `withdrawn`，未命中的学生志愿标记为 `rejected`。
6. 对每名调剂录取学生，在原 `applications` 表中复用或创建目标课题申请并写为 `accepted`，并写入“来自调剂志愿”的操作日志与通知。首次志愿的优先级、理由和首次结算记录不删除；课题状态及教师总指导上限在同一事务内重新校验和更新。
7. 成功或未匹配均发送站内通知；状态、日志和通知任一写入失败时，正式结算事务回滚，结算记录保留为 `failed` 供管理员重试。

## 6. 接口与页面

### 6.1 学生接口

- `GET /api/adjustment-volunteers/eligible-topics`：仅返回当前周期、学生本人专业、仍有名额的已发布课题。
- `GET /api/adjustment-volunteers/mine`：返回学生的调剂志愿、状态与结算摘要。
- `PUT /api/adjustment-volunteers/mine`：整组保存 3–6 个调剂志愿，提交前允许覆盖更新。

### 6.2 教师接口

- `GET /api/adjustment-volunteers/topics/:topicId/draft`：读取本课题调剂名单、批次、排序、学生档案摘要及仅供展示的技能/兴趣匹配提示。
- `PUT /api/adjustment-volunteers/topics/:topicId/draft`：乐观锁保存完整草稿。
- `POST /api/adjustment-volunteers/topics/:topicId/submit`：提交本课题名单并检查是否可结算。

### 6.3 管理员接口

- `GET /api/admin/adjustment-settlement/:cycleId`：读取调剂提交进度和结算状态。
- `POST /api/admin/adjustment-topics/:topicId/unlock`：结算开始前退回教师名单。
- `POST /api/admin/adjustment-settlement/:cycleId/run`：满足条件时手动结算或重试失败结算。

### 6.4 页面

- 重写 `src/views/student/Adjustment.vue` 为“调剂志愿”工作台，去除单课题申请弹窗和调剂记录。
- 新增教师调剂遴选页与路由，仅在调剂阶段显示操作区。
- 新增管理员调剂结算页；保留 `adjustments` 历史记录只读，不再提供审批按钮。
- 学生结果页把“参与调剂”入口指向新的调剂志愿工作台。
- 学生端所有选题相关页面移除教师信息展示；教师和管理员页面维持现有展示字段。

## 7. 约束、并发与兼容

- 后端是阶段与权限的最终约束；非 `adjustment` 阶段的调剂志愿、教师草稿、提交和结算操作返回 `409`。
- 教师草稿与学生调剂志愿保存都使用 `version`；同一资源的旧版本写入返回 `409`。
- 结算使用每周期 MySQL 命名锁，保证并发实例只有一个结算执行者；已完成周期返回已有结果。
- 教师保存和提交前重新验证课题余量与教师总上限；结算事务再次验证，避免并发超额。
- 调剂志愿一经结算开始即冻结；服务器在截止时停机并重启后，启动检查补做自动提交和结算。
- 旧 `/api/applications/adjustments` 写入与审批接口返回 `410`，前端不再调用；历史 `adjustments` 数据不删除。
- 学生选题接口采用角色化响应，学生响应不含教师身份字段；教师、管理员响应保留原字段。

## 8. 验收场景

1. 未录取学生看到本专业内全部有空位发布课题；其他专业课题不可见。
2. 已录取学生不能进入调剂志愿提交。
3. 少于 3 个、多于 6 个、重复、跳号或仅一位教师的志愿组被拒绝。
4. 学生整组更新后，教师重新读取名单只看到最新志愿和理由。
5. 教师页面显示技能、兴趣、个人陈述、志愿序号、技能/兴趣匹配提示和草稿决定；保存草稿不改变正式结果。
6. 教师提交后只读，管理员在结算前退回后可再编辑。
7. 最后一个有申请课题提交时，只执行一次调剂结算。
8. 截止自动提交未处理草稿；未处理学生不会被系统猜测为拟录取或候补。
9. 同一学生被多个课题拟录取时，只保留其调剂志愿序号最高的结果，释放名额按候补顺序递补。
10. 课题余量、教师总上限与一生一题在保存、提交和结算中均不被突破。
11. 结算失败后正式结果全部回滚，管理员重试后只产生一份最终结果。
12. 调剂录取后，首次志愿的优先级、理由和首次结算日志仍可追溯，且调剂来源在操作日志与通知中明确记录。
13. 学生在任一阶段浏览选题或查看选题结果时均看不到教师身份信息；教师、管理员页面和数据库记录保持不变，学生志愿的两位教师覆盖校验仍有效。

## 9. 发布与回滚

- 上线前备份数据库和上传目录，保存当前 `adjustments`、`applications`、课题名额和首次结算统计。
- 发布后核对新增表、调剂截止任务日志、教师调剂页、管理员进度页及学生调剂页。
- 应用代码异常可回滚镜像或源码；若调剂结果已写入且业务异常，使用发布前数据库备份恢复，不得通过再次结算覆盖。
