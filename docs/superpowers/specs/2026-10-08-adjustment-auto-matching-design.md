# 调剂补录学生志愿自动匹配设计

**状态：用户已批准；实施与上线部署已授权**

## 1. 目标

将调剂阶段由“学生填报—教师逐课题遴选—统一结算”改为“学生填报—系统按学生志愿自动匹配”。本设计仅改变调剂补录，不改动首次志愿和首次遴选。

## 2. 已确认规则

- 资格：本周期参加过首次志愿填报、遴选结束时没有任何正式录取的学生。已有任一 `accepted` 课题的学生不参加。
- 可选课题：当前周期、本专业、已发布；该课题当前录取人数低于课题容量；其指导教师本周期录取总人数低于教师指导上限。未配置教师总上限时沿用系统现有的“不限”语义。
- 志愿：学生可选 1–6 个不同课题，按个人偏好排列；不要求覆盖多位教师。允许在截止前修改，使用现有版本校验和整组保存。
- 匹配时点：沿用当前周期调剂截止时间，在截止后统一匹配。截止前只保存志愿，不提前写入正式录取，避免学生仍可修改时结果被固化。
- 学生竞争同一课题：使用周期内可复核的确定性随机优先序，不按提交先后或 GPA 排序。
- 约束：一名学生最多录取一个课题；每课题不超过容量；教师本周期总录取不超过配置上限。

## 3. 匹配规则

采用学生提议式逐轮匹配。每位尚未匹配的学生依其志愿序号向下一顺位课题提出申请；每轮中课题与其指导教师共同按剩余容量暂留优先序靠前的候选，落选学生继续申请下一志愿。被暂留学生若后来被更高优先序申请人挤出，会释放名额并继续申请下一顺位。没有可申请志愿或最终未获名额的学生标记为未匹配。

随机顺序由周期 ID、教师 ID、学生 ID 通过固定哈希规则生成；同一教师不同课题的竞争使用一致的教师/学生优先序，从而可共同执行教师总名额约束。该顺序不依赖运行时随机数或数据库返回顺序。同一周期重试得到同一优先序，操作日志记录算法版本和结果摘要以便复核。

## 4. 流程与状态

1. 调剂阶段开放后，符合资格的学生查看可选课题并保存 1–6 个有序志愿。
2. 学生可修改志愿直到截止时间；截止后服务端拒绝保存。
3. 到截止时间，现有截止任务触发一次性结算；没有任何志愿时正常完成空结算。
4. 结算在事务和周期命名锁内重新读取学生资格、课题容量、教师录取人数及指导上限，再运行自动匹配。
5. 命中志愿写入正式 `applications` 录取；命中调剂志愿标记 `accepted`，同一学生其他志愿标记 `withdrawn`，未匹配志愿标记 `rejected`。保留首次志愿和历史 `adjustments` 记录。
6. 结算完成后通知学生录取课题或未匹配结果，并通知相关教师和管理员。

## 5. 页面与接口调整

- 学生调剂页移除“两位教师覆盖”校验，数量下限改为 1；明确展示当前课题容量和教师剩余指导名额条件、截止时间及结算状态。
- 学生端和服务端均采用相同的资格与课题过滤规则，后端复核所有提交项，避免伪造课题 ID 或名额状态过期。
- 教师“调剂遴选”页面及调剂草稿写入接口不再参与本轮录取；旧数据表和记录保留，不删除、不迁移。旧教师页面在调剂阶段改为只读说明或安全重定向。
- 管理员调剂页面展示符合资格学生数、志愿数、截止时间、结算状态和自动匹配结果；不再要求每个课题提交教师名单，也不提供提前执行结算入口。失败结算保留受限重试入口。
- 旧批次、草稿项及历史操作日志保留作为审计资料，不参与新自动匹配。

## 6. 并发、安全与失败处理

- 志愿提交继续采用事务、乐观版本和截止时间校验。
- 结算开始后冻结本周期所有调剂志愿。结算先在单事务内检查录取冲突并锁定相关周期、课题、学生记录。
- 自动匹配结果须再次遵守当前容量和教师指导上限；数据状态与保存时不一致时，以结算时锁定状态为准。
- 结算使用现有命名锁和幂等状态；事务失败时正式录取、志愿状态、课题状态、通知和日志均回滚，结算记录标记失败，可由管理员重试。
- 已完成结算不可覆盖或重复通知；部署不自动执行生产数据库迁移或生产结算。

## 7. 兼容与发布边界

- 保留旧表结构和既有数据，不删除 `adjustment_batches`、`adjustment_draft_items` 或 `adjustments`。
- 旧教师提交接口应明确返回已停用状态，前端不再调用；旧草稿不参与自动匹配。
- 数据库 schema 无新增字段需求时，不增加迁移；若实现发现必须新增字段，先停止并更新本设计。
- 本次实现修改代码、执行本地构建与匹配逻辑检查，并按项目现有 GitHub Actions 主分支流程上线 GPSS。
- 上线前按 `docs/adjustment-volunteers-release-checklist.md` 备份生产数据库和上传目录，保存调剂周期、首次录取、课题及教师名额基线；上线后检查健康接口和角色流程。
- 本次不手工修改生产数据，不执行调剂结算；系统仅按已配置的截止时间自动触发新匹配逻辑。
- 部署脚本仅重建 GPSS 服务，不应重建半山学堂。Actions 在 `main` 收到代码提交后触发生产部署；仅部署本次明确纳入的文件。

## 8. 验收场景

1. 未被首次遴选录取且有首次志愿记录的学生有资格；已录取、无首次志愿记录的学生无资格。
2. 学生只看到本专业、发布中、课题未满且指导教师未达总上限的课题；提交时后端重新校验。
3. 1 个及 6 个志愿可保存；0 个、超过 6 个、重复课题、非本专业或已满课题被拒绝；仅一位教师的多个志愿可提交。
4. 截止前可以修改；截止后或结算开始后不可修改。
5. 学生优先顺序决定其匹配结果；课题竞争由确定性随机顺序裁决。高志愿匹配成功后不保留低志愿；高志愿落空后继续尝试低志愿。
6. 多课题共享同一教师上限时，结果仍同时满足每课题容量和教师总上限。
7. 每名学生最多录取一个课题；未匹配、接受、撤回状态和通知与正式结果一致。
8. 截止触发与管理员失败重试均保持幂等；结算事务失败不留下半套正式结果。
9. 教师无需提交调剂名单，旧草稿及历史记录仍可保留查看但不影响自动匹配。
