# GPSS 遴选草稿、自动提交与统一录取设计

日期：2026-09-26  
状态：已通过（2026-09-27）
适用系统：GPSS

## 1. 背景与目标

当前系统由教师逐条执行“接受、待定、拒绝”。低志愿录取受更高志愿未处理状态阻塞；教师长期不处理时，学生无法继续流转。现有 `waitlisted` 在教师网页端成为不可继续操作的状态，审核截止也没有独立定时任务。系统允许 3–6 个志愿，但教师页面只定义前三个志愿的中文标签。

本次改造目标：

1. 教师可以保存拟录取、候补和不录取草稿，不提前改变学生正式结果。
2. 教师可以主动提交课题名单；全部课题提交后提前统一结算。
3. 到达审核截止时间后，系统自动提交剩余草稿并统一结算。
4. 统一结算同时尊重学生志愿顺序、教师选择、课题容量和教师指导上限。
5. 候补可以继续调整并在统一结算时自动递补。
6. 第 1–6 志愿在所有页面、接口和导出中正确显示和校验。
7. 所有提交、自动提交、解锁、结算与异常均可审计、可重试。

## 2. 已确认业务规则

### 2.1 教师草稿

每条申请在教师草稿中可处于以下决策之一：

- `proposed`：拟录取；
- `reserve`：候补，必须有候补顺序；
- `reject`：不录取；
- 未保存决策：未处理。

草稿对学生不可见，不修改 `applications.status`，也不撤回该生其他志愿。教师可以反复保存和调整草稿。

### 2.2 名单提交

教师按课题提交名单。提交后：

- 该课题的草稿被锁定；
- 页面显示“已提交，等待统一结算”；
- 结算前只有管理员可以退回该课题重新修改；
- 提交行为本身不直接生成 `accepted`；
- 当前周期所有有申请的课题均已提交时，立即启动统一结算。

没有申请的课题不要求教师提交，系统视为已完成。

### 2.3 截止自动提交

审核截止时间沿用周期配置中的 `review_deadline`、`teacher_review.end` 或 `review.end`。进入教师遴选阶段前必须存在有效截止时间；缺失时管理员页面显示阻断提示。

截止时：

- 已保存的草稿按原内容提交；
- 未作决策的申请视为不录取；
- 完全没有草稿的课题不自动录取任何学生；
- 系统不得推测教师意图或按 GPA 自动录取；
- 自动提交后立即启动统一结算。

### 2.4 正式结果

统一结算完成后：

- 每名学生最多录取一个课题；
- 获得录取的申请写为 `accepted`；
- 该生同周期其他未终结志愿写为 `withdrawn`；
- 教师明确不录取、未作决定且最终无录取的申请写为 `rejected`；
- 所有志愿均未录取的学生进入调剂范围；
- 满额课题写为 `full`，仍有名额的课题保持 `published`。

## 3. 统一匹配算法

### 3.1 输入

- 当前周期有效申请及其 `priority`；
- 教师提交的 `proposed`、`reserve`、`reject`；
- 每个课题的 `max_students`；
- 周期的教师指导学生总上限；
- 教师为拟录取和候补设置的顺序。

GPA 不参与系统录取，申请时间也不作为择优依据。教师未明确排序且发生同级并列时，仅用申请时间和申请 ID 作为确定性兜底，保证重复执行得到同一结果。

### 3.2 匹配过程

1. 每个课题生成教师选择序列：`proposed` 在前，`reserve` 在后，各自按教师排序。
2. 课题按选择序列向学生提供名额，最多不超过课题容量。
3. 同一学生收到多个课题意向时，只保留自己志愿序号最小的课题，释放其他名额。
4. 释放名额的课题继续向下一名候补提供名额。
5. 重复步骤 2–4，直到没有录取变化。
6. 结算前再次校验一生一题、课题容量和教师总上限。
7. 在单个数据库事务中写入最终状态、课题状态、操作日志和通知。

### 3.3 教师总指导上限

教师总上限是跨该教师全部课题的共享容量。进入遴选阶段前，管理员必须处理“课题名额总和大于教师上限”的配置冲突。系统在保存草稿、提交名单和最终结算三个位置重复校验；发生冲突时阻止提交或结算，并明确列出教师、已分配名额和上限，不静默删减教师选择。

## 4. 数据模型

保留 `applications` 作为学生申请和最终结果表，新增三个表，避免把教师草稿混入正式状态。

### 4.1 `selection_batches`

每个周期、每个课题一条：

- `id`；
- `cycle_id`；
- `topic_id`；
- `status`：`draft | submitted | auto_submitted | settled`；
- `version`：每次保存递增，用于防止两个页面覆盖；
- `submitted_by`、`submitted_at`；
- `auto_submitted_at`；
- `settled_at`；
- `created_at`、`updated_at`；
- 唯一键：`cycle_id + topic_id`。

### 4.2 `selection_draft_items`

每个申请最多一条草稿决策：

- `id`；
- `batch_id`；
- `application_id`；
- `decision`：`proposed | reserve | reject`；
- `decision_rank`；
- `comment`；
- `updated_by`；
- `created_at`、`updated_at`；
- 唯一键：`batch_id + application_id`。

### 4.3 `selection_settlements`

每个周期最多一条正式结算记录：

- `id`；
- `cycle_id`；
- `status`：`pending | running | completed | failed`；
- `trigger_type`：`all_submitted | deadline | admin_retry`；
- `result_json`：录取、落选、调剂人数摘要；
- `error_message`；
- `started_at`、`completed_at`；
- 唯一键：`cycle_id`。

数据库初始化采用兼容现有生产库的 `CREATE TABLE IF NOT EXISTS`。部署前必须先备份数据库。历史周期不迁移，只处理当前进行中周期。

如果当前周期存在 `waitlisted`：部署前先统计数量；迁移时在事务内创建对应 `reserve` 草稿，并将原申请恢复为 `pending`。`accepted`、`rejected`、`withdrawn` 历史结果不自动改写。

## 5. 后端接口

### 5.1 教师接口

- `GET /api/applications/topics/:topicId/selection-draft`：读取课题草稿、版本和提交状态；
- `PUT /api/applications/topics/:topicId/selection-draft`：保存整份草稿，要求版本匹配；
- `POST /api/applications/topics/:topicId/submit-selection`：提交并锁定名单；
- 现有逐条“直接接受”接口不再供教师页面调用，避免绕过统一结算。

### 5.2 管理员接口

- `GET /api/admin/selection-settlement/:cycleId`：查看各课题提交进度和结算状态；
- `POST /api/admin/selection-topics/:topicId/unlock`：结算前退回教师修改；
- `POST /api/admin/selection-settlement/:cycleId/run`：满足条件时手动结算或失败后重试。

所有写接口均校验当前周期、当前阶段、课题归属、教师权限、版本、容量和指导上限，并写入 `operation_logs`。
管理员退回后，批次状态恢复为 `draft`；退回动作和原因只保存在操作日志中，不增加额外业务状态。

## 6. 截止任务与幂等

不新增定时任务依赖。服务启动后立即检查一次，之后每分钟检查审核截止状态。

执行规则：

1. 使用 MySQL 命名锁保证同一周期只有一个结算执行者；
2. 查询截止且尚未完成的周期；
3. 自动提交所有未提交批次；
4. 创建或锁定 `selection_settlements`；
5. 执行统一匹配事务；
6. 写入完成摘要并释放锁；
7. 服务在截止时不可用的，恢复启动后自动补执行；
8. 已 `completed` 的周期直接返回既有结果，重复触发不重复写入。

管理员页面提供“立即检查”和“失败后重试”，但不能对已完成结算重复执行。

## 7. 页面设计

### 7.1 教师遴选页

- 每行提供“拟录取、候补、不录取、清除决定”；
- 拟录取和候补支持拖动排序；
- 顶部显示名额、拟录取数、候补数、未处理数、教师总上限和截止倒计时；
- “保存草稿”不会影响学生正式状态；
- “提交本课题名单”显示影响说明并二次确认；
- 已提交状态只读，显示提交时间和提交方式；
- 候补仍可在草稿阶段继续改为拟录取或不录取。

### 7.2 管理员页面

- 展示教师、课题、申请人数、草稿进度、提交状态、最后保存时间；
- 突出未保存、未提交和配置冲突；
- 支持结算前退回；
- 展示自动任务最后执行时间、结算结果和失败原因。

### 7.3 学生页面

结算前统一显示“等待教师遴选/统一录取”，不展示拟录取和候补草稿。结算完成后显示唯一正式结果；未录取学生显示调剂入口和原因说明。

## 8. 第 1–6 志愿修复

1. 页面统一直接显示 `第 ${priority} 志愿`，删除只覆盖前三项的中文映射。
2. 前后端共享 3–6 个志愿的业务含义，各自集中定义 `VOLUNTEER_MIN` 和 `VOLUNTEER_MAX`，不在页面散落硬编码。
3. 后端新增连续性校验：提交 N 个志愿时，排序必须恰好为 `1..N`。
4. 检查学生工作台、教师遴选、管理员申请数据、结果页、通知和 Excel 导出。
5. 页面数量统一显示“已填 N 个，至少 3 个、最多 6 个”，不再把 `/3` 表达为固定总数。

## 9. 状态迁移与兼容

- 新流程启用后，教师页面不再直接调用逐条 `accepted/rejected/waitlisted` 操作；
- 正式结算仍写入现有 `applications.status`，学生结果页和后续任务书流程继续使用 `accepted`，减少下游改动；
- 已经完成录取的历史周期保持原状；
- 当前周期若已有正式 `accepted`，结算时将其视为锁定结果，不重新分配，并占用对应课题和教师名额；
- 旧浏览器调用直接录取接口时返回清晰提示，要求刷新并使用新版遴选流程；管理员紧急处理必须走有审计的专用入口。

## 10. 异常与回滚

- 草稿保存使用版本号防止覆盖较新的编辑；
- 容量或教师上限冲突时停止提交/结算，不产生部分正式结果；
- 统一结算所有正式状态变更位于同一事务，失败全部回滚；
- 结算失败保留草稿、提交记录和错误信息；
- 发布前备份数据库和上传目录；
- 应用回滚时保留新增表，旧版本不会读取它们；
- 若需业务回滚，使用部署前数据库备份恢复，不能通过再次结算覆盖。

## 11. 验收场景

实施完成后，在隔离数据库中至少核对：

1. 3、4、5、6 个连续志愿均可提交，跳号被拒绝；
2. 第 4–6 志愿在教师、学生、管理员页面和导出中正确显示；
3. 教师保存草稿不改变学生正式状态；
4. 候补可继续调整，提交后锁定；
5. 所有课题提前提交后只结算一次；
6. 未全部提交时，到期自动提交并结算；
7. 无草稿课题不会自动录取学生；
8. 学生同时获得多个教师意向时进入最高志愿；
9. 高志愿未录取后，低志愿拟录取可自动生效；
10. 拟录取学生进入更高志愿后，候补按顺序补位；
11. 不超过课题容量和教师总上限；
12. 已录取学生不被重复录取；
13. 服务在截止时间停机，恢复后能够补结算；
14. 重复触发、并发触发不会产生第二份结果；
15. 结算失败不会留下部分录取状态；
16. 管理员退回、手动重试、操作日志和通知正常。

## 12. 不在本次范围

- 使用 GPA、作品集或算法评分替教师决定录取顺序；
- 学生查看教师草稿或候补排名；
- 跨周期匹配；
- 自动调剂到学生未填报的课题；
- 修改毕业设计后续任务书、开题、中期、答辩和成绩流程。
